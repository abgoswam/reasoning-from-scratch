Where Amulet Keeps Things

A Singularity job is five separate Azure components that have to cooperate. Knowing which one you are looking at — and which subscription it sits in — explains both where a job runs cleanly and where it stalls.

5 components per job 2 clusters, both verified 2 meanings of "queued" ssh is a submit-time decision

1 · The five components

Amulet's vocabulary makes sense only once you see that a running job is assembled from five independent Azure resources. They are provisioned separately, permissioned separately, and can live in different subscriptions and regions.

2 · Co-location — why the same job behaves differently on two clusters

Those five components were provisioned together for the South Africa cluster: one subscription, one resource group, one region. Aiming the same job at a cluster in a different subscription keeps four of the five where they were and moves only the compute.

queued means two different things. It covers both waiting for a free node and staging the image onto one, and nothing in the CLI distinguishes them. The status can even flap queued → running → queued while an image settles. Do not read amlt target info as cluster occupancy — it reports your consumption against your entitlement, so 3 / 96 means three of your own jobs, and says nothing about how many nodes other people are using.

Rule for a far cluster

Prefer a Manifold platform image — amlt cache base-images. Short alias, no registry: field, resolved per-target by Singularity, so nothing crosses a region.

If you need your own image

It works — cold staging a multi-GB image took ~70 min, then ~10 min on a node that already had it. The cache is per node, so a later job landing elsewhere pays full price again.

4 · The local binding

Amulet is directory-bound. There is no global "current project" — a hidden .amltconfig sits in a folder and amlt reads it from wherever you stand. Unlike git it does not walk up to a repo root; unlike az it keeps no single global default.

Field in .amltconfigComes fromConsequence
project_uuidcloudIdentical in every folder bound to this project
created · n_experimentscloudShared history — every checkout sees the same experiments
project_default_workspacecloudworkspace set-project-default writes to the project, so a fresh checkout inherits it
default_configlocalPer-folder — a fresh checkout does not inherit it
local_path · default_output_dirlocalYour current directory, frozen at checkout time

Many-to-one, and unlocked. Any number of folders on any number of machines can bind to one project simultaneously. None knows about the others; nothing is reserved.

The rename trap. Move the folder and local_path / default_output_dir point somewhere that no longer exists. Re-running amlt project checkout does not fix it — it sees an active project and short-circuits with "already checked out". Repair with amlt project set default-output-dir ./amlt, verify with amlt project.

CommandWhat it does

Phase 8 · Monitor and collect

CommandWhat it does
amlt status <exp>All jobs in the experiment with duration, status, size and cluster. Column positions shift as jobs progress — parse by header name, never field number.

12 · Interactive jobs and SSH

A batch job ends when its command ends. An interactive box is the opposite: it exists to stay up so a person can log into it. That needs two things the cluster does not provide by default — a process that never exits, and enough GPU activity that the cluster does not reclaim the node.

Prerequisites for amlt ssh

RequirementDetail
amlt run -iSingularity enables sshd only on jobs declared interactive. A job submitted without -i can never be reached, however healthy it looks.
a key in ~/.sshAmulet sends the first key it finds at submission. If none exists, ssh is silently disabled for that job — no warning at submit, and amlt ssh simply hangs later.
VPN / corpnetRequired to reach Singularity nodes at all.
a real key fileKeys forwarded through ssh-agent are not supported.
no retrofitBoth conditions are fixed at submit time. A running job that lacks them must be cancelled and resubmitted.

The shape of the job

jobs:
  - name: interactive
    sku: 80G1-H100
    command:
      - set -e -o pipefail
      - mkdir -p "$$AMLT_OUTPUT_DIR"
      - while true; do python gpu_keepalive.py --interval 60 --burst 5; sleep 5; done
          2>&1 | tee -a "$$AMLT_OUTPUT_DIR/keepalive.log" &
      - nvidia-smi
      - sleep infinity

The keepalive runs a short burst of large matrix multiplications each minute rather than one quick operation, so that utilization sampling cannot miss it — roughly an 8% duty cycle against a two-minute idle threshold, with two cycles inside every window. It is wrapped in a respawn loop because a crashed keepalive would let the GPU fall idle and the job be reclaimed, which presents as an unexplained disappearance rather than an error.

set -e does not protect a background process, and tee rather than a plain redirect keeps the heartbeat visible in amlt logs view as well as persisted to blob storage.

Working with the box

submit — note the -i
amlt run -i interactive.yaml :interactive <experiment> --sla Premium --yes

confirm the heartbeat before relying on it
amlt logs view -n 40 <experiment> :interactive

connect, optionally forwarding a port
amlt ssh <experiment> :interactive
amlt ssh <experiment> :interactive -o "-L 8888:localhost:8888"

nothing reclaims it but you
amlt cancel <experiment> :interactive

An interactive box holds its GPU until cancelled. There is no timeout and no idle expiry once the keepalive is doing its job — that is the point of it, and also the hazard. On a shared cluster, cancel what you are not using.

13 · Cluster and image compatibility

Which combinations of cluster, workspace and image actually produce a running job. The image column is the only one that changes the outcome once the workspace is one you can submit through.

ClusterWorkspaceImageResultNotes
ai-frontiers-sa-vcai-frontiers-sa-wsteam ACR, in-regionworksThe co-located stack. No staging cost; queue length is pure node contention.
baltic01ai-frontiers-sa-wsplatform imageworks~5 min queue. The recommended combination for a far cluster.
baltic01ai-frontiers-sa-wssmall ACR, cross-regionworks~10 min queue for a ~50 MB image. Proves the cross-subscription pull path is open.
baltic01ai-frontiers-sa-wsmulti-GB ACR, cross-regionworks~70 min to stage onto a cold node, ~10 min onto a warm one. Delay only.
baltic01gcrllm2wsanyrejectedFails at submit: datastores/write denied. Needs the AzureML Data Scientist role.

What this establishes

  • A workspace can drive a VC in another subscription. The job is accepted, allocated quota, scheduled and run. No special configuration is required.
  • The identity and storage account travel with the workspace, not the cluster. A node in Singularity Shared authenticated as ai-frontiers-id and read and wrote aifrontierssadata without additional role assignments.
  • Cross-subscription registry pulls are permitted. The registry has public network access, no IP rules and no private endpoints; a small image from it runs on a foreign cluster.
  • Image size and distance are the practical constraint. A multi-GB CUDA image staged from southafricanorth to eastus2 did not complete within 30 minutes, while the same registry's 50 MB image completed comfortably.
  • Registering a workspace does not confer the right to submit through it. amlt workspace add needs only Reader; submission needs AzureML Data Scientist.

What remains unknown

How far the image cache reaches. A multi-GB image took ~70 minutes to stage onto a cold node and ~10 minutes on a later submission, which is consistent with either a per-node cache that happened to be reused or a cluster-level mirror. A third submission queued far longer again, which favours the per-node reading. Plan for the cold cost recurring; treat a fast start as luck rather than entitlement.
