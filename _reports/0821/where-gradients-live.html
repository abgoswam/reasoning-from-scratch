00The file

ch06/01_main-chapter-code/trials_14_grad_and_step.py · no model, no GPU, instant

Everything in this document comes from one expression, chosen so that every gradient is a number you already know:

x = torch.tensor([1., 2.])                     # input data
w = torch.tensor([3., 4.], requires_grad=True) # learnable
b = torch.tensor(0.5, requires_grad=True)      # learnable

tmp1 = w * x        # [3., 8.]
tmp2 = tmp1.sum()   # 11.0
tmp3 = tmp2 + b     # 11.5   -- this IS y

# dy/dw = x = [1., 2.]      dy/db = 1.0      dy/dx = w = [3., 4.]

Writing it one operation at a time is the whole trick. (w * x).sum() + b on a single line hides two intermediate tensors that have their own identity, their own flags, and their own node in the graph. Give them names and every question below answers itself in the debugger.

01Who gets a .grad

Part 1 · trials_14_grad_and_step.py:48

Two conditions, both required. "Learnable" is not one of them — PyTorch has no concept of a parameter at this level.

  tensor             value  is_leaf  req_grad grad_fn                .grad
  ------------------------------------------------------------------------
  x             [1.0, 2.0]     True     False None                    None
  w             [3.0, 4.0]     True      True None              [1.0, 2.0]
  b                    0.5     True      True None                     1.0
  tmp1          [3.0, 8.0]    False      True MulBackward0      [1.0, 1.0]
  tmp2                11.0    False      True SumBackward0             1.0
  tmp3 (=y)           11.5    False      True AddBackward0             1.0

Read the columns in order and the structure falls out:

  • is_leaf splits the table in half. The three tensors you typed are leaves; the three that came out of an operation are not. "Leaf" just means nothing produced this.
  • requires_grad is contagious forward. x is False, yet tmp1 = w * x is True — one operand requiring grad is enough, and once true it stays true downstream.
  • grad_fn is the exact mirror of is_leaf. Leaves have None; non-leaves each carry the node that differentiates the op that made them.
  • .grad is filled for w and b only.

The tutorial settles the "learnable" question by running the toy a second time with requires_grad=True on the input data. x2.grad comes back as [3.0, 4.0], which is w, because dy/dx = w. Input tensors get a gradient the moment you ask for one — the same mechanism behind adversarial examples and input-gradient saliency.

Those intermediate .grad values are borrowed

tmp1, tmp2 and tmp3 only show a value because Part 1 calls retain_grad() on them first. Remove it and all three read None while w.grad is still correct. Their gradients are calculated — backward cannot reach w without them — but they are consumed by the chain rule and dropped in the same instant.

02How the graph is built

Part 2 · trials_14_grad_and_step.py:133

The usual confusion here comes from imagining a compiler: some pass that inspects your function and constructs a graph from it. That is not what happens. There is no build step. PyTorch records as it executes, one operation at a time, on the way forward.

Each op does four things:

  1. Computes its output, the ordinary numeric work.
  2. If any input requires grad, allocates one backward node.
  3. Fills that node's next_functions with references to where each input came from.
  4. Hangs the node off the output tensor as its .grad_fn.

So the graph grows from the bottom up while your code runs — and it can only ever point backwards, because at the moment a node is created the later operations have not happened yet. There is nothing forward to point at.

The rule, in one line

Once you see how a node is wired, the whole structure is mechanical. For a new node created by an op with inputs i₀, i₁, …:

next_functions[i] = inputs[i].grad_fn              # input i is a non-leaf
                  = AccumulateGrad(inputs[i])     # leaf that requires grad
                  = None                          # anything else

That first case is literal identity, not resemblance. Part 2 checks it:

after tmp2 = tmp1.sum()
  tmp2.grad_fn                        : SumBackward0
  next_functions[0] IS tmp1.grad_fn   : True

after tmp3 = tmp2 + b
  tmp3.grad_fn                        : AddBackward0
  next_functions[0] IS tmp2.grad_fn   : True
  next_functions[1].variable is b     : True

A new node does not describe the previous op — it holds the same object. That is what makes the chain a chain, and it is why the whole thing is freed the moment nothing references the final tensor.

03Reading it back

Part 2 · walk_graph at trials_14_grad_and_step.py:119

Laid flat, forward and backward are the same line-up walked in opposite directions. Each forward tensor sits directly above the node its operation created.

walk_graph prints the same structure as an indented tree, which is what the recursion naturally produces:

AddBackward0
  next_functions[0] = SumBackward0
    SumBackward0
      next_functions[0] = MulBackward0
        MulBackward0
          next_functions[0] = AccumulateGrad
            AccumulateGrad   -> writes .grad of the leaf [3.0, 4.0]
          next_functions[1] = None   (input needs no gradient)
  next_functions[1] = AccumulateGrad
    AccumulateGrad   -> writes .grad of the leaf 0.5

Three things worth pinning down

  • next_functions is badly named. It is not "the next operation" — it is where do I hand my gradient next. The name describes the backward walk, not the forward one.
  • The tuple is positional. next_functions[i] belongs to input i of the forward op, which is why MulBackward0 has two slots even though only one leads anywhere. A None slot is a real entry, not an absence — printing that filters Nones will make MulBackward0 look like it has one input.
  • AccumulateGrad is where .grad is written. It holds the real tensor in .variable and performs p.grad += incoming. That += lives here, in the graph — not in the optimizer. Which is exactly the behaviour section 04 is about.

The None under MulBackward0 also closes the loop on the empty quadrant in section 01. No node was ever created for x, so its gradient is not computed-then-discarded — the graph simply has no path to it. That is what makes requires_grad=False a genuine compute saving rather than just a flag.

04.grad accumulates

Part 3 · trials_14_grad_and_step.py:180

backward() does p.grad += new, not p.grad = new — that is the AccumulateGrad node doing its job. Calling backward three times on the same graph:

before any backward : None
after backward #1   : [1.0, 2.0]
after backward #2   : [2.0, 4.0]
after backward #3   : [3.0, 6.0]
after w.grad = None : None

This is deliberate: it lets you split a large batch across several backward calls and have the gradients add up correctly. The report on Two Ways to Backward covers a case where that is exactly the point.

The cost is that a forgotten zero_grad() does not raise anything. It silently trains on the sum of this step's gradient and every previous one — a bug that shows up as mysteriously unstable training, not as an error.

05What step() does

Part 4 · trials_14_grad_and_step.py:205 · Part 5 · :254

Less than you would think. The optimizer holds references to the very same tensor objects — optimizer.param_groups[0]['params'][0] is w returns True — and it never touches the graph at all. It reads p.grad, writes p.data. For plain SGD the update is reproducible by hand, exactly:

w before step : [3.0, 4.0]
w.grad        : [1.0, 2.0]
w after step  : [2.9000000953674316, 3.799999952316284]
w - lr*w.grad : [2.9000000953674316, 3.799999952316284]   ← identical

Two details that catch people:

  • step() does not clear .grad. After stepping, w.grad is still [1.0, 2.0]. Clearing is a separate call, which is why zero_grad() opens the next iteration rather than closing this one.
  • AdamW is not lr · grad. Part 4 prints its state — exp_avg, exp_avg_sq, step — running averages the optimizer owns. But .grad is still its only input from the graph; everything else is the optimizer's own memory.

Clipping sits in between

clip_grad_norm_ rewrites .grad in place, after backward has filled it and before the optimizer reads it. Part 5 takes a gradient of norm 50 down to norm 1:

.grad before clip : [30.0, 40.0]  norm=50.00
.grad after clip  : [0.6, 0.8]    norm=1.00

Direction preserved, magnitude capped. In RLVR this is not boilerplate — advantages come from (r − mean) / (std + 1e-4), and when almost every rollout scores zero and one gets lucky, that 1e-4 floor is the only thing between you and an enormous update.
