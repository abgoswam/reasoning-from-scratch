Two Ways to Backward

The book stacks every rollout's log-probability and calls backward() once. Your SWE-bench notebook calls it once per rollout. The gradients come out identical to float precision — but one holds N graphs in memory and the other holds one.

01The two loops

book: trials_00.py:143–183 + :291 · notebook: swe_grpo_one_step.ipynb cell 42

Same objective, same math, different placement of one call.

A — accumulate graphs, one backward

# trials_00.py, compute_grpo_loss
for _ in range(num_rollouts):
    token_ids, prompt_len, text = sample_response(...)
    logp = sequence_logprob(model, token_ids, prompt_len)
    roll_logps.append(logp)          # graph stays alive

logps   = torch.stack(roll_logps)     # :180 — all N graphs still resident
pg_loss = -(advantages.detach() * logps).mean()

# trials_00.py, train_rlvr_grpo
stats["loss_tensor"].backward()       # :291 — one call, frees all N

B — backward per rollout, accumulate gradients

# swe_grpo_one_step.ipynb, cell 42
opt.zero_grad(set_to_none=True)
for g, a in zip(group, adv):
    lp, _ = seq_logprob(g["messages"])
    loss  = -(a.to(DEV) * lp) / len(group)   # pre-divided → total is a mean
    loss.backward()                       # this rollout's graph freed HERE
    loss_total += loss.item()

The pivot is that backward() frees the graph it walks, unless you pass retain_graph=True. In B that happens N times, each time releasing the rollout that just finished. In A nothing is freed until the very end, because roll_logps still holds a reference to every scalar — and a reference to a scalar keeps the entire graph behind it alive.

02What memory does

the whole difference, in one picture

Everything backward() needs from a rollout — the saved activations, the log-softmax output, the retained keys — can be released the instant that rollout's contribution has been folded into .grad. Strategy B takes that option. Strategy A declines it, for no benefit here.

03The shared funnel

why two different traversals land in the same place

Each forward pass builds its own chain of nodes — a fresh MulBackward0, a fresh SumBackward0, a fresh everything. Those chains never touch each other. But they all end at the same node.

PyTorch caches exactly one AccumulateGrad per leaf tensor and hands that same object to every graph that touches it. It is created the first time a parameter is used in a differentiable op, and never rebuilt:

SumBackward0 nodes distinct : True
MulBackward0 nodes distinct : True

AccumulateGrad(w) SHARED    : True
  ...and it is the canonical one for w: True     # == get_gradient_edge(w).node

That single picture explains both halves of this report. Everything left of the divider is per-rollout, so strategy A holding N of them costs N times the memory. Everything right of it is shared and constant-size, so .grad is identical either way.

How the shared node fires

The two strategies reach that node by different routes, and the node behaves differently in each. Counted with a hook registered directly on it:

strategy A: AccumulateGrad(w) executed 1 time(s)
strategy B: AccumulateGrad(w) executed 3 time(s)
w.grad A  : [0.667, 0.667]
w.grad B  : [0.667, 0.667]
identical : True

04Why they produce the same gradient

gradient accumulation, from the other direction

The loss is a mean over rollouts, and a mean is a sum of independent terms:

       −(A · logp).mean()   ==   Σᵢ  [ −(Aᵢ · logpᵢ) / N ]
       └──── one graph ────┘        └── N separate graphs ──┘

Term i touches only rollout i's graph. Differentiation is linear, so the gradient of the sum equals the sum of the gradients — which is precisely what .grad += … computes across N backward calls. That is why backward() accumulates rather than assigns: this decomposition is the common case, not an edge case.

Checked rather than assumed — same weights, same inputs, both strategies:

loss A             : -0.12545899
loss B (summed)    : -0.12545899
gradients identical: True
max abs diff       : 2.98e-08          # float32 rounding, nothing more
The division is load-bearing

/ len(group) inside the loop is what makes the accumulated total a mean rather than a sum. Drop it and every gradient is N× too large — with N = 6, an effective learning rate six times what you set. The book gets the same normalization for free from .mean(); strategy B has to spell it out.

05What a rollout's graph actually costs

Abstract until you price it. The dominant term is not the transformer — it is the vocabulary projection at the end. Measuring only the out_head → .float() → log_softmax → gather chain for Qwen3-0.6B (vocab 151,936):

The culprit is log_softmax saving its own [T, 151936] float32 output for backward — 607 KB per token on that tensor alone. Extrapolated to a real rollout of 614 tokens (102-token prompt + 512 generated), and counting only this chain, not the 28 transformer layers:

Your training job has 44.4 GiB free on cuda:3 and runs --num-rollouts 4, so strategy A costs you roughly 10 GB of headroom you are not using for anything. It is also the concrete reason the notebook's advice — “to get a relatively good model, it requires at least num_rollouts=8” — collides with its own implementation: at 8 rollouts strategy A is spending ~27 GB on graphs that could have been ~3.4 GB.

Read this as a lower bound

The figure covers the output-head chain only. Add the 28 transformer layers' saved activations and the true per-rollout number is higher — which widens the gap rather than narrowing it. The point is the multiplier on N, not the exact constant.

06When you can't do it per rollout

the condition that makes B legal

Strategy B is valid only because the loss decomposes — no term couples two rollouts inside the graph. Break that and B stops being an optimization and starts being a bug.

In this chapter's GRPO neither loss has such a term. Advantages come from rewards that are plain Python floats, so they enter as constants — which is what the .detach() at trials_00.py:183 documents. Chapter 7 adds a KL penalty, and that stays per-token against a frozen reference model, so it decomposes too.

Note that PyTorch does not silently produce a wrong answer here. Coupling plus per-rollout backward raises RuntimeError: Trying to backward through the graph a second time. The failure mode is loud.

and what the book is buying with the other choice

For this workload B is strictly better and your notebook has it right. The extra N−1 backward launches are microseconds against a rollout that took seconds to generate.

What A buys is pedagogy, and that is a defensible reason in a book. pg_loss = -(advantages.detach() * logps).mean() is the GRPO objective written as one readable line, with the group-relative structure visible in the shapes: advantages and logps are both [num_rollouts], and .mean() is the group average. Strategy B scatters that same equation across a loop body, where the / len(group) reads like a detail rather than the definition. The book is optimizing for the reader; you were optimizing for the GPU.

If you want B in the book's loop

The change is contained. Move the backward inside compute_grpo_loss's rollout loop, drop roll_logps, and divide by num_rollouts in the per-rollout loss. You lose stats["loss_tensor"], so train_rlvr_grpo at trials_00.py:291 stops calling .backward() and goes straight from the loss computation to clip_grad_norm_. Everything downstream — clipping, step(), the CSV metrics — is untouched, because .grad looks exactly the same either way.
