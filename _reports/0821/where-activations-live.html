Where Activations Live

A tensor that autograd “saves” is not stored anywhere new. It is pinned exactly where it already was — and following that pin is the whole story of why grad-enabled generation costs 28 GiB at 512 tokens.

source ch06/01_main-chapter-code/trials_12_activations.py torch CPU, float32 toys numbers measured, not estimated

00 — Orientation

What the script is actually teaching

Three parts, one instrument, one conclusion. Each part answers a single question, and each question is a prerequisite for the next. The script is not three demos — it is one argument in three moves.

01 — The instrument

How retained_bytes counts

Every number in this report comes from one 24-line walker. It starts at out.grad_fn, does a depth-first traversal over node.next_functions, and for each node reads every attribute whose name starts with _saved_. Those are PyTorch’s Python-side windows onto the C++ node’s saved-variable slots.

The one subtlety that makes the numbers honest: it dedupes by storage.data_ptr(), not by tensor identity. Two tensors that are views of the same buffer get counted once. That is why Part 2 reports 30.25 MiB and not the naive 36 MiB — each ReLU output is literally the same memory as the next layer’s matmul input.

# the whole instrument
stack = [out.grad_fn]
while stack:
    node = stack.pop()
    for attr in dir(node):
        if attr.startswith("_saved_"):          # ← the window into the C++ node
            v = getattr(node, attr)
            if torch.is_tensor(v):
                s = v.untyped_storage()
                if s.data_ptr() not in storages:  # ← dedupe by BUFFER, not tensor
                    total += s.nbytes()
    for nxt, _ in node.next_functions:            # ← walk the graph edges
        stack.append(nxt)

Part 1  ·  Question 1

For y = q @ k.T, where exactly is the activation kept?

Your question

“Where exactly are the saved tensors kept? y = q @ k.T — where is the activation tensor saved to be used in the backward pass?”

Short answer

Nowhere new. The MmBackward0 node — a C++ object on the heap, owned by y through its grad_fn pointer — holds two SavedVariable slots that reference the buffers q and k already own. No copy is made. The cost is not extra bytes allocated; the cost is bytes that cannot be released.

The script proves this in one line: y.grad_fn._saved_self is q returns True, and _saved_mat2.data_ptr() == k.data_ptr() also returns True.

Here is the full chain of custody. Read it left to right: a Python name, an autograd node, a raw buffer.

Verified: deleting the Python name does not free the memory

The script implies this; a probe confirms it. After del k and a forced gc.collect(), node._saved_mat2.data_ptr() still returns the original address. The buffer is alive because the graph node is its owner of record.

And the moment the graph is consumed, the pins release. Calling y.sum().backward() and then touching node._saved_self raises:

RuntimeError: Trying to backward through the graph a second time
(or directly access saved tensors after they have already been freed)

That error message is usually read as an annoyance. It is actually the memory-release event, made audible.

02 — Part 1, continued

Why those two tensors, and not others

The script’s header comment gives the rule, and the rule fully determines the saving. For Y = Q Kᵀ:

∂L/∂Q  =  (∂L/∂Y) @ K needs K, so it stores → _saved_mat2
∂L/∂K  =  (∂L/∂Y)ᵀ @ Q needs Q, so it stores → _saved_self

Read that carefully, because the cross-over is the interesting part: _saved_mat2 (which is k) exists to compute the gradient of q, not of k. Autograd saves an operand for the sake of the other operand’s gradient.

Which yields a testable prediction: turn off requires_grad on one input, and the other input stops being saved. It holds exactly:

q.requires_gradk.requires_gradMmBackward0 savesbecause
TrueTrue_saved_self, _saved_mat2both rules are live
TrueFalse_saved_mat2only ∂L/∂Q is needed → only K kept
FalseTrue_saved_selfonly ∂L/∂K is needed → only Q kept

Autograd is not conservatively hoarding the forward pass. It saves the minimum the live backward formulas name — and that minimum is exactly what you pay for. This is the mechanism behind a number you will meet in Part 2, where seven weight matrices are retained out of eight.

Part 3  ·  Question 3

Why incremental blew up and full-sequence didn’t

Your question

“Why did incremental blow up but not full-seq?”

Short answer

Both compute the same numbers. But incremental decoding computes them from T different buffers and full-sequence computes them from one.

At decode step t, torch.cat([prev_k, k_new]) allocates a brand new tensor of length t — it does not extend the old one in place. Then the matmul on the next line pins that new buffer. So you end up holding buffers of length 1, 2, 3, … T simultaneously. They are logically prefixes of each other, but physically they are T separate allocations. Summed: 1+2+…+T = T(T+1)/2.

The full-sequence pass runs one matmul over the whole [H, T, D] key tensor. One buffer, pinned once, length T.

The tempting wrong answer is “cat is expensive because autograd saves the concatenation”. It isn’t — you saw in the table above that CatBackward0 saves nothing at all. The cost is one step downstream: cat materialises a fresh buffer, and BmmBackward0 keeps it alive.

Part 3  ·  Question 2

“Both sides are quadratic” — what that line means

Your question

“For part 3 you said both sides are quadratic. I don’t get it?”

Short answer

It is a claim about the ratio, not about either side individually. Since incremental and full-sequence both grow like T², their ratio is a ratio of two quadratics — which converges to a constant instead of growing without bound.

So the ratio column in the script’s table (19× → 33× → 52× → 74×) is not on its way to infinity. It is climbing toward a ceiling of 128.5× and will never pass it. That is what “grows sub-linearly” means: it grows, but with ever-decreasing speed, because the denominator eventually catches up.

Term by term

Here is the accounting from the script, split into its three components. H = 16 heads, D = 128 head-dim, 2 bytes per bf16 element, 28 layers.

Row two is the sentence you asked about. The full-sequence pass has a T² term too — its one [H, T, T] attention matrix per layer. That is what stops the ratio from running away.

Take the limit and the constant falls out. Keep only the T² terms:

incremental  ≈  (2·H·D·2 + H·2) · T²/2      # triangle → T²/2
full-seq     ≈  (H·2) · T²                  # full square

ratio  →  (2·D + 1) / 2  =  (2·128 + 1) / 2  =  128.5×

The 2·D is keys and values, each D = 128 numbers wide. The 1 is the single attention scalar. The /2 is the triangle being half a square. Everything in that expression is visible in the geometry figure above.

Watch the ratio flatten

The curve steepens through the range the script tabulates (32–512), which is exactly why 19× → 74× looks unbounded. Extend the x-axis and it turns over. Hover any point for the exact value.

Why the bounded ratio doesn’t save you

Here is the trap the script is warning about. “Only a bounded constant worse” sounds reassuring, and it is completely irrelevant — because both curves are quadratic, and a quadratic in absolute terms is already fatal. Watch the two lines on a log axis:

07 — the payoff

What the codebase does instead

The fix is not a smaller cache or gradient checkpointing. It is to decline the trade entirely: never build a graph during generation, then build exactly one graph afterwards over the finished sequence.

Which closes the loop on the script’s opening question. sample_response runs under @torch.no_grad() because a graph over T decode steps is a T²/2 triangle of key-value rows. The logprob is recomputed in one teacher-forced pass because that pass puts only a 2-byte scalar in the quadratic bucket, and pins the key-value tensor exactly once.
